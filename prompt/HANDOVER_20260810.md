# VR Flat Player

<img src="../assets/icon-256.png" width="128" alt="VR Flat Player">

在**普通显示器**上舒服地看 180/360 VR 视频的桌面播放器。支持本地 8K。
可选：用普通摄像头追踪头部动作来自动转视角。

**当前版本 0.2。**（仓库目录名还是 `VRHeadTrackingPlayer`，改名只改了软件本身，
没动 git 路径。）解码和渲染复用 mpv + mpv360，本仓库提供播放器窗口和中间的追踪桥接层。

```
                          VRFlatPlayer.exe
  ┌─────────────────────────────────────────────────────────┐
  │  原生菜单栏   媒体 播放 音频 字幕 VR 视图 帮助           │
  ├─────────────────────────────────────────────────────────┤
  │                                                         │
  │   mpv 的窗口（--wid 子窗口，另一个进程）                │
  │     mpv360 投影着色器 · uosc 控制栏 · Tab 模式面板      │
  │                                                         │
  └─────────────────────────────────────────────────────────┘
        ▲                                    ▲
        │ JSON IPC                           │ 左键拖动（Win32 直接读鼠标）
        │                                    │
   ┌────┴─────────────────────────────────────┴────┐
   │  桥接层：One Euro 滤波 / 增益曲线 / 回中      │
   └───────────────────────┬───────────────────────┘
                           │ UDP（可选）
                  opentrack ◄── webcam
```

## 为什么是这个架构

- **8K 必须走原生解码。** 浏览器的 HEVC 硬解不可靠，8K 逐帧上传纹理也没有零拷贝保证。
  mpv 把 8K HEVC/AV1 硬解、seek、音轨、字幕全部解决了。
- **mpv360**（MIT）已经实现了 GPU 上的等距柱状/鱼眼/EAC 投影着色器，不用自己写。
- **opentrack** 内置 NeuralNet 追踪器，无标记点、开箱即用，输出标准 UDP。追踪算法一行不用写。

桥接层做的是这三者之间没人做的那部分：**把头部角度变成让人不晕的视角角度。**

### 桥接层如何控制 mpv360

mpv360 的 Lua 命令表只有**相对**步进（`look-left`、`look-up`…），对绝对头部追踪没用。
但它最终是通过这个属性把状态推给着色器的：

```
change-list glsl-shader-opts add "mpv360/yaw=..,mpv360/pitch=..,mpv360/roll=.."
```

所以桥接层直接写同一个属性，就拿到了绝对控制权，**不需要 fork mpv360**。
代价：mpv360 自己的按键（Ctrl+方向键、鼠标视角）保留着独立的状态副本，运行期间同时用会打架。
约定：**yaw/pitch/roll 归桥接层管，FOV / 投影格式 / 眼别归 mpv360 管。**

## 两台机器怎么分工

这是本项目的实际开发约束：8K 测试机（RTX 5060 Ti）没有摄像头，有摄像头的是笔记本。
`--source` 抽象就是为此存在的。

| 场景 | 机器 | 命令 |
|---|---|---|
| 先确认 opentrack 真的在发包 | 笔记本 | `VRFlatPlayer --source=udp --dump` |
| 真摄像头 + 4K，调手感 | 笔记本 | `VRFlatPlayer --source=udp "D:\clips\test4k.mp4"` |
| 录一段真实头部动作 | 笔记本 | `VRFlatPlayer --source=udp --record=recordings/lookaround.csv "D:\clips\test4k.mp4"` |
| 8K + 回放真实动作 | 5060 Ti | `VRFlatPlayer --replay=recordings/lookaround.csv "E:\vr\clip8k.mp4"` |
| 8K + 鼠标假装头部 | 5060 Ti | `VRFlatPlayer --synthetic=mouse "E:\vr\clip8k.mp4"` |

### 更省事的办法：把笔记本当成无线头部追踪器

两台机器在同一局域网时，不用录制回放——**笔记本跑 opentrack，UDP 直接发到台式机**，
就能一边真实追踪一边播 8K：

1. 笔记本 opentrack → Output 选 **UDP over network** → 填台式机的局域网 IP，端口 `4242`
2. 台式机放行入站 UDP 4242：
   ```powershell
   New-NetFirewallRule -DisplayName "headtrack UDP" -Direction Inbound -Protocol UDP -LocalPort 4242 -Action Allow
   ```
3. 台式机：`VRFlatPlayer --source=udp "E:\vr\clip8k.mp4"`

局域网多出的延迟在 1ms 量级，对平面屏幕头追完全无感。

## 安装

1. **.NET 8 SDK**（这台机器目前只有 1.1/2.1 的 SDK，必须先装）
   ```bash
   winget install Microsoft.DotNet.SDK.8
   ```
2. **mpv**（shinchiro 构建，含 `vo=gpu-next`）
   ```bash
   winget install shinchiro.mpv
   ```
   这个包**不会**把 mpv 加进 PATH（装在 `C:\Program Files\MPV Player\`）。
   桥接层会自动探测常见安装位置，一般不用管；装在别处就在
   `bridge.config.json` 的 `mpv.mpvPath` 填绝对路径。
3. **mpv360**（脚本 + 着色器，MIT）
   ```powershell
   powershell -ExecutionPolicy Bypass -File tools\install-mpv360.ps1
   ```
4. **opentrack**（只有笔记本需要）：<https://github.com/opentrack/opentrack/releases>
   - Input: **Neuralnet tracker**
   - Output: **UDP over network**
   - 摄像头不在屏幕正中时，用 NeuralNet 的 camera-offset 补偿

编译并运行：

```bash
dotnet run --project src/HeadTrackBridge -- "E:\vr\clip8k.mp4"
```

没有片源也能验证整条链路（lavfi 生成 2:1 测试图）：

```bash
dotnet run --project src/HeadTrackBridge -- --synthetic=sweep "av://lavfi:testsrc2=size=1920x960:rate=30"
```

mpv 自己的输出被重定向到 `mpv-last-run.log`（否则它的进度行会和桥接层的状态行打架）。
播放出问题先看这个文件。

### 打开文件的几种方式

- **把视频拖到 `VRFlatPlayer.exe` 上** —— 直接播
- **双击 exe** —— 起一个空播放器，用菜单栏「媒体 → 打开文件」或 `Ctrl+O`
- **菜单栏「媒体 → 关闭文件」** —— 只关文件，播放器留着（`mpv.conf` 里 `idle=yes` +
  `force-window=yes` 两个都要有：前者决定窗口在不在，后者决定播放列表空了以后 mpv 还活不活着）
- **注册到"打开方式"**（只写 HKCU，不需要管理员，也不会抢走你现有的默认播放器）：
  ```bash
  powershell -ExecutionPolicy Bypass -File tools\register-file-association.ps1
  ```
  撤销加 `-Unregister`。

## 打包发布

双击 **`publish.bat`**，或者：

```bash
powershell -ExecutionPolicy Bypass -File tools\publish.ps1
```

开发时跑源码用 **`run.bat`** —— 可以直接把视频拖到它上面，也可以带参数
（`run.bat --source=udp "D:\clips\test4k.mp4"`）。

> 两个 bat 内部**只用英文**。cmd.exe 是按控制台的 OEM 代码页读取 .bat 的，
> 里面写中文在多数机器上会变成乱码，所以说明都放在这里。

产出 `dist\VR Flat Player 0.2\`（约 262 MB）和同名 zip（约 173 MB）：

```
VR Flat Player 0.2/
  VRFlatPlayer.exe          单文件，自带 .NET 运行时
  bridge.config.json        默认设置
  README.md
  THIRD-PARTY-NOTICES.txt
  mpv/
    mpv.exe                 打包进去的播放引擎
    d3dcompiler_43.dll
    mpv.conf  input.conf  scripts/  shaders/  fonts/  script-opts/
```

**用户不需要另外装任何东西** —— mpv 和 .NET 运行时都在包里，解压即用。

### 系统要求

默认包是**自包含**的，`.NET 8` 运行时打在里面（`VRFlatPlayer.runtimeconfig.json` 里
`includedFrameworks` 同时列了 `Microsoft.NETCore.App` 和 `Microsoft.WindowsDesktop.App`
就是这个意思）。**用户机器上装没装 .NET 完全不影响。**

但"自带运行时"不等于"什么机器都能跑"，真正的下限是这三条：

| | 要求 | 说明 |
|---|---|---|
| 系统 | **Windows 10 1607 及以上 / Windows 11** | .NET 8 本身的下限，自带运行时也绕不过去。**Win7 / Win8.1 跑不了** —— 微软在 .NET 8 里去掉了对它们的支持，最后支持它们的 .NET 6 也已停止维护 |
| 架构 | **x64** | 默认只出 x64。ARM64 机器加 `-Runtime win-arm64` 单独打一个（会生成独立的目录和 zip，不会覆盖 x64 的那个） |
| 显卡 | **支持 D3D11 的 GPU** | `mpv.conf` 里 `vo=gpu-next` + `gpu-api=d3d11` + `hwdec=d3d11va`。**实际更容易卡住用户的是这条**，不是 .NET |

碰到显卡问题不用改配置文件，**菜单里就能换** —— 见下面一节。

### 如果非要用小体积的包

```bash
publish.bat -FrameworkDependent
```

代价是**用户必须自己装 .NET 8 Desktop Runtime**（注意是 **Desktop**，不是普通 Runtime
—— WinForms 在 Desktop 包里，装错了照样起不来）。没装的话双击会弹一个微软的提示框，
带下载链接，不会静默失败。产物目录带 `net8-required` 后缀，免得和自包含的包搞混。

**但省不了多少：实测 205 MB → 137 MB。** 因为大头根本不是 .NET，是 mpv.exe
那 120 MB（静态编译，把所有解码器都链进去了）。为 68 MB 换来一整类"用户装错运行时"
的支持成本，不划算。真想瘦身应该从 mpv 那边下手，不是从 .NET。

`mpv.exe` 放在 `mpv/` 里面是故意的：这个目录同时是引擎和它的 `--config-dir`，
所以"我们打包的这套 mpv"是一个可以整体替换或删除的单元，而 `ResolveMpvPath`
本来就最先找这个位置。

几个开关：

| 参数 | 作用 |
|---|---|
| `-FrameworkDependent` | 不打包 .NET（205 → 137 MB），但用户得自己装 .NET 8 **Desktop** Runtime |
| `-NoSingleFile` | 输出一堆 DLL 而不是单个 exe（想单独替换某个程序集时用） |
| `-MpvExe <路径>` | 指定要打包的 mpv，默认自动找本机的 |
| `-NoZip` | 只出目录不打包 |

发布前脚本会先检查 `mpv/scripts/uosc`、`mpv360.lua`、`shaders/`、`fonts/` 在不在 ——
这几样是 `install-mpv360.ps1` 下载的、不在 git 里，漏了的话打出来的包会没有控制栏也没有 360，
而且要等用户打开文件才发现。

### 版本号

只在一个地方改：`HeadTrackBridge.csproj` 里的 `<InformationalVersion>`。
关于框、控制台横幅、发布目录名、zip 名都从那里读，不会互相对不上。
（旁边的 `<Version>` 是 Windows 要求的四段式 `FileVersion`，一起改。）

### 图标

改了图标要重新生成，构建只是把 `assets\icon.ico` 原样嵌进去：

```
tools\make-icon.bat
```

形状定义在两个地方，**必须同步改**：`assets/icon.svg` 是母版（README、网页、商店页面用），
`tools/make-icon/Program.cs` 用 GDI+ 画同一套形状。之所以要画两遍，是因为 Windows 上
没有现成的 SVG 光栅化器，而 `.ico` 只能是位图 —— 与其让图标流程依赖一个外部工具，
不如让两份共用同一套 256 网格上的坐标常量。

图标不是一张图缩小九次。**32px 以下会切换到另一套几何**：两侧的追踪弧线在那个尺寸
细过一个像素，鼻梁缺口也会糊死，所以小尺寸干脆去掉弧线，把护目镜和播放三角放大占满整块。
`.ico` 里 256/128 存 PNG（体积小，资源管理器认），64 及以下存传统 DIB（少数老的图标读取器
会跳过 PNG 条目）。

设计上三个形状各管一件事：护目镜轮廓 = VR 内容，里面的播放三角 = 这是个播放器，
两侧的弧线 = 摄像头在看着你。弧线是唯一一个要一形两义的：当成头戴设备的一部分它是头带
（正是它让护目镜不至于看着像电视），单独看它是感应波纹，对应人脸追踪和体感手势。

### 许可证：打包 mpv 是有义务的

mpv 是 GPL。**分发 mpv 的二进制**就要说明这是哪个构建、源码在哪 —— 脚本会自动把
mpv 的确切版本号（`v0.41.0-244-gaf9c81fa1` 这种）和上游地址写进 `THIRD-PARTY-NOTICES.txt`。
发布页上把 mpv 源码链接一并放出来就合规了。

我们自己的代码不受影响：播放器是**把 mpv 当独立进程启动、走 JSON IPC 通信**的，
没有链接任何 mpv 代码 —— 当初选进程分离而不是链接 libmpv，一半的理由就是这个。

### 路径里有空格会打爆 mpv360（已修）

发布目录叫 `VR Flat Player 0.1`，**带空格**，第一次打出来的包所有 VR 模式全部失效 ——
画面永远是 2D，点任何模式都没反应。mpv 日志里只有一行：

```
[input] Command change-list has trailing unused arguments: ' Flat Player 0.1\mpv/shaders/mpv360.glsl'
```

mpv360 上游是这么加载着色器的：

```lua
mp.command("no-osd change-list glsl-shaders append " .. config.shader_path)
```

**mpv 会把字符串形式的命令按空格拆开**，于是路径在第一个空格处被截断，着色器根本没加载。
`install-mpv360.ps1` 现在会把它改成 `mp.commandv(...)`（参数分开传，不拆分）。

这个坑不只影响我们：**任何 Windows 用户名带空格**的人（配置目录 `C:\Users\John Smith\AppData\Roaming\mpv`）
都会中招。值得提个 issue 给上游。

发布目录名**故意保留空格**，这样这个 bug 一旦回归就会立刻暴露。

排查这类问题的第一步永远是看 `glsl-shaders` 这个属性到底是不是空的：

```
{"command":["get_property","glsl-shaders"]}   # 经 \\.\pipe\vrheadtrack
```

### 安装到 Program Files 也能用

配置和状态默认就放在 exe 旁边（绿色版）。但如果程序装在只读目录里，
会自动改用 `%APPDATA%\VR Flat Player\`，启动时会打印一行说明。
判断方式是**真的去写一个探测文件**，不是猜路径 —— 权限不是能从路径名推出来的东西。

## 显卡跑不动怎么办：菜单里换解码和渲染器

「播放 → 硬件解码 / 渲染器」。这是给**默认设置在某台机器上跑不起来**的情况准备的，
不用碰配置文件。

### 解码和渲染器不是两个独立的选择

这一点很反直觉，但踩过一次就明白：**解码出来的画面是一张 GPU 纹理，渲染器必须能接住它。**
接不住的话 mpv 会退回软件解码，而且**什么都不说**。

最典型的就是 NVDEC：它走 CUDA 互操作，在默认的 d3d11 后端上会被拒绝 ——

```
[vo/gpu-next/cuda] CUDA hwdec only works with OpenGL or Vulkan backends.
hwdec = ["nvdec"]        <- 设置"成功"了
hwdec-current = "no"     <- 实际在跑软解
```

所以解码菜单里会**直接标出哪几项和当前渲染器不兼容**（「需要 opengl 渲染器」），
选了不兼容的会弹框问你要不要连渲染器一起换。

| 解码 | 需要的 GPU API |
|---|---|
| Direct3D 11 / DXVA2 | d3d11 |
| NVDEC | opengl 或 vulkan |
| Vulkan | vulkan |

### 硬件解码（立即生效）

默认 / 自动 / Direct3D 11 / DXVA2 / NVDEC / Vulkan / 软件解码。改了当场重新初始化解码器。

**第一项「默认」= 不覆盖，跟随 `mpv.conf`（也就是 `d3d11va`）。**
它排在"自动"前面并且标着推荐，是因为 `mpv.conf` 里那个值是**实测选出来的**，
而 mpv 的 `auto`/`auto-safe` 可能落到 copy-back 路径上 —— 8K 下 17 fps 对 32.7 fps。
把"自动"当成推荐项等于推荐慢的那个。选「默认」也是从任何试错状态回到已知良好配置的办法。

菜单标题上带的是 **mpv 实际在用的那个**（读 `hwdec-current`），不是你选的那个。
这个区别很重要 —— **设置 `hwdec` 永远会"成功"**：mpv 接受这个名字，初始化失败就
悄悄退回软解，唯一能看出来的地方就是 `hwdec-current`。实测：

```
hwdec=nvdec  ->  设置成功，hwdec 读回 "nvdec"，hwdec-current 读回 "no"
```

（nvdec 是 CUDA 互操作路径，在 d3d11 后端上会被拒绝。）如果你选了硬解却掉回软解，
播放器会直接告诉你「xxx is not available here — using software」，而不是让你以为提速了。

### 渲染器（重启后生效）

一条从好到通用的退路，**画面全黑或卡顿时从上往下逐个试**：

| | vo | gpu-api |
|---|---|---|
| 默认 | `gpu-next` | d3d11 |
| 兼容 | `gpu` | d3d11 |
| OpenGL | `gpu` | opengl |
| ANGLE | `gpu` | opengl + angle 上下文 |
| Direct3D 9 | `direct3d` | — |

**`Ctrl+Shift+B` 直接切下一档** —— 这个快捷键存在的理由就是：需要它的时候画面是黑的，
而看不见的菜单没法用。切完会问你要不要现在重启。

**为什么不能立即生效：** `vo` 单独改是可以热切换的，但底下的 `gpu-api` 不行 ——
mpv 的图形上下文是视频输出初始化时一次性建立的，之后再设 `gpu-api` 会被接受但什么都不会重建
（实测切到 opengl 之后日志里仍然是 `[vo/gpu/d3d11]`）。
只应用能应用的那一半反而更糟：上表里有三档**只差 API**，全都会"看起来成功但毫无变化"，
用户挨个试完会以为一档都没用。所以老老实实重启。

## 播放器窗口

播放器是**我们自己的窗口**，顶部是一条真正的 Windows 菜单栏，mpv 画在下面的面板里：

```
媒体(F)  播放(P)  音频(A)  字幕(S)  VR(V)  视图(W)  帮助(H)
```

这么做的唯一原因就是这条菜单栏。mpv 只能在自己的画面里作画，所以它能提供的一切控件
（自带 OSC、uosc、我们的 vrmenu）都是**画在画面上的**。要一条画面之外的菜单栏，
就必须由我们持有顶层窗口，再用 `--wid` 把 mpv 的窗口挂成它的子窗口。

菜单里的东西都不是新功能，是把已有能力摆到看得见的地方：VR 菜单里的投影 / 立体 / 眼别 / FOV
和 `Tab` 模式面板是同一套状态，勾选状态每次打开菜单时现算，所以不会和播放器实际状态脱节。
音轨、字幕轨列表是打开菜单时向 mpv 现查的。

全屏（`F`）会自动收起菜单栏。窗口初始大小按**实际 DPI** 算 —— 这台机器 300% 缩放，
不这么做会得到一个 1280×760 物理像素的小窗口配一套正常大小的菜单字。

加 `--detached` 可以退回"mpv 自己开窗口、桥接层当旁挂进程"的老模式。
它不是遗留代码，是嵌入出问题时的退路，也是 `--no-launch` 挂到你自己起的 mpv 上时的唯一方式。

### 嵌入 mpv 时踩到的三个坑

`--wid` 不是挂上去就完事，三件事必须由宿主补：

1. **键盘焦点过不了进程边界。** mpv 的窗口是另一个进程的子窗口，Windows 不会把键盘焦点
   交给它，所以在播放器里敲任何键 mpv 和 uosc 都收不到。宿主接管键盘，把按键翻译成 mpv 的
   键名后经 IPC `keypress` 转发（`Host/KeyMap.cs`）。好处是键位仍然只在 `input.conf` 里定义一处。
2. **mpv 把子窗口建成了 `WS_DISABLED`**（实测 style `0x58000000`）—— 它假定嵌入方自己处理输入。
   被禁用的窗口收不到任何鼠标消息，症状是 **uosc 永远不出现**、进度条点不动、
   mpv 的 `mouse-pos` 恒为 `{x:0, y:0, hover:false}`。宿主把它重新 `EnableWindow` 就好了，
   这比自己转发鼠标事件好：mpv 拿到的是真实的 `WM_MOUSEMOVE`/滚轮和正确的 hover 跟踪，
   uosc 的行为和独立 mpv 完全一致。因为 mpv 重建窗口时会再禁用一次，这个检查每 250 ms 跑一遍。
   反过来，菜单展开时要把子窗口**禁用回去**：WinForms 是靠自己消息循环上的过滤器来
   "点别处收起下拉菜单"的，而点在另一个进程的子窗口上根本进不了这个循环，下拉菜单就一直挂着。
   开菜单期间把子窗口关掉，点击自然落到我们的面板上 —— 这是把原生行为还回去，不是模仿它。
3. **mpv 没法把子窗口全屏。** 所以 mpv 只持有 `fullscreen` 这个**状态**，宿主负责**效果**：
   监听该属性，变了就自己改窗口。这样 uosc 的全屏按钮、mpv 的 `f`、菜单里的"全屏"走的是同一条路。

鼠标不需要转发，这点值得记一笔：鼠标消息按光标位置投递，和焦点无关。

## 调参

配置在 [bridge.config.json](bridge.config.json)。

### 滤波（One Euro）

不用固定低通也不用卡尔曼：One Euro 在慢动作时重滤波（消掉无意识微抖），
快动作时轻滤波（转头不拖影）。调参顺序**必须**是：

1. `beta = 0`，把 `minCutoff` 往下调到静止时画面不再游移
2. 再把 `beta` 往上调到快速转头不再有拖拽感

### 增益曲线

```
输出角度 = sign(n) · |n|^curve · outputRange     其中 n = clamp(相对头部角度 / inputRange, -1, 1)
```

`curve = 1.8` 意味着中心附近响应很软（小幅晃头几乎不动画面，等于一个不会产生跳变的软死区），
越往边缘增益越高（头转 25° 能看到 150° 外的东西）。这比线性 + 硬死区舒服得多。

### 三条经验值

- **`roll.outputRangeDegrees` 默认 0，别打开。** 画面倾斜是晕动症头号来源，而人歪头是无意识的。
- **pitch 增益要明显小于 yaw**（默认 70° vs 150°）。人对垂直方向错位敏感得多。
- **信号丢失时冻结，绝不回中。** `trackingTimeoutSeconds` 到了只冻结画面 + OSD 提示。

## 界面语言

跟随 Windows 显示语言，无需配置。

原因值得记一笔：**mpv 和 uosc 都不读操作系统语言**。uosc 的 `languages` 默认是
`slang,en`，而 `slang`（字幕语言偏好）在正常安装下是空的，所以不管系统是什么语言都会
落到英文。桥接层是唯一能看到 `CultureInfo.CurrentUICulture` 的组件，由它解析一次，
再通过 `--script-opts-append` 同时喂给 uosc 和我们自己的脚本。

目前有 **英文 / 简中 / 繁中 / 日文 / 韩文**。想固定语言就改 `bridge.config.json` 的
`ui.language`（`auto` / `en` / `zh-CN` / `zh-TW` / `ja` / `ko` / `de` …）。

中文判断用的是**文字系统而不是地区**：`zh-SG` 是简体、`zh-MO` 是繁体，只看国家码两个都会错。

### i18n 一共四个地方

加语言要四个都动，漏一个就是"只翻译了一半"：

| 文件 | 管什么 |
|---|---|
| `src/HeadTrackBridge/Localization.cs` | 系统语言 → 语言标签，再喂给 mpv / uosc / vrmenu |
| `src/HeadTrackBridge/UiStrings.cs` | 菜单栏、对话框、**画面上的提示文字** |
| `mpv/scripts/vrmenu.lua` 的 `STRINGS` | Tab 模式面板 |
| `mpv/uosc-intl/*.json` | uosc 控制栏 |

`mpv/scripts/uosc/` 是 gitignore 的（`install-mpv360.ps1` 整个重装），所以我们自己写的
uosc 翻译**不能放那里**。放在 `mpv/uosc-intl/`（纳入版本管理），安装脚本每次运行都会
拷进去 —— 包括"skip (exists)"那条路径，这样加语言不需要 `-Force`。
uosc 上游没有日文和韩文，这两个是我们写的。

### "中文只翻译了一半"是怎么来的

`UiStrings.cs` 以前叫 `MenuStrings.cs`，只管菜单栏。**桥接层打在画面上的所有提示都是
调用点上硬编码的英文字面量** —— 头部追踪开关、解码器切换、渲染器切换、VR 模式播报。
菜单是中文的，视频上飘过去的字是英文的。

现在凡是用户能读到的字都在 `UiStrings.cs` 里，而且**单元测试会比对各语言的 key 集合**：
少一个 key 会静默回退到英文，写字符串的人根本看不出来，只能靠机器比。占位符也一起查
（`{0}` 被翻译弄丢就是解码器名字凭空消失，多一个 `{2}` 就是 `FormatException`）。

日文和韩文的翻译是我写的，没有母语者校对过，有不地道的地方欢迎直接改表。

## 记住每个文件的模式

选过一次就记住，下次打开直接用。存在 `mode-memory.json`，按完整路径的哈希索引
（不明文记录你看过什么）。

**这比改进自动识别更有价值**：mono 360 和 VR180 左右排列都是 2:1，流里没有任何信息能
区分，识别永远是在猜文件名，总有一部分片子会猜错。记住之后，"每次打开都错"变成"只错一次"。

优先级：`--projection` 命令行参数 > 记住的选择 > 自动识别。关掉用
`ui.rememberPerFileMode: false`。

从 uosc 菜单、播放列表或拖拽打开新文件时会重新识别 —— 播放器的生命周期比单个文件长，
不重新识别的话第二个文件会沿用上一个的投影。

**只有你手动改过的模式才会被记住。**

### 优先级

打开一个文件时，从强到弱依次询问，前面有答案就不问后面的：

| # | 来源 | 含义 |
|---|---|---|
| 1 | `--projection` / 配置 | 你现在、显式地，为这一次运行指定 |
| 2 | 该文件的记忆 | 你以前，为这个文件选过 |
| 3 | **确信的识别** | 文件名有可识别的标记，或分辨率只可能是一种排布 |
| 4 | **上次用过的模式** | 你以前，为别的文件选过 |
| 5 | 默认值 | `video.fallback`，默认 `vr180`（180 / 3D 左右） |

第 3 步的"确信"是关键：识别**分不出来的时候会说自己分不出来**，而不是硬猜一个。
以前 2:1 一律当 360，等于有一半时间是错的 —— 而且错的方向更难受：
VR180 当成 360 看起来像一张扭曲的重复画面，不像明显的报错。

第 4 步（`video.stickyMode`，默认开）解决的是"一整个文件夹编码方式一样"的情况：
改一次，后面的都跟着走。它只填第 3 步没有答案的空档，永远压不过识别和单文件记忆。

**"说不准"只有 2:1 一种情况。** 一个 mono 360 球面和两只并排的正方形 VR180 眼睛
铺出来的矩形完全一样,只有这时才需要往下问粘性和默认值。

**其他比例、文件名又没线索的，一律按平面 2D 播。** 16:9、4:3、2.39:1 电影、
9:16 竖屏 —— 这些都不是 VR 排布，这仍然是个视频播放器，不能因为上一个文件是 VR
就把一部普通电影糊到球面上。

**平面永远不会成为粘性模式。** 它的含义是"这个文件不是 VR"，是那个文件的属性，
不是一种偏好；存下来的话，看一部普通电影就会把下一个真正的 VR 文件的 VR 关掉。

### 文件名识别规则

合并了 DeoVR、HereSphere、SKYBOX 三家的命名约定。标记**两侧必须是非字母数字**
（`_`、`-`、`.`、空格或开头结尾），所以 `movie_1080p`、`640x360`、`s01e02_360p`
都不会被误判 —— 这是三家里 HereSphere 的规则，最严谨。

| 类别 | 标记 |
|---|---|
| 投影 180 | `180`、`vr180`、`180x180`、`180sbs`、`half-equirect` |
| 投影 360 | `360`、`equirect`、`equirectangular` |
| 鱼眼（镜头型号） | `f180` / `180f`、`fisheye190` / `rf52`、`mkx200`、`mkx22`、`vrca220` |
| 鱼眼（通用） | `fisheye`、`dual-fisheye` |
| EAC | `eac360`、`360eac`、`eac` |
| 柱面 | `cylindrical`、`cylinder`（我们自己加的，三家都没有） |
| 左右 | `sbs`、`hsbs`、`lr`、`lrf`、`3dh`、`side-by-side`、`left-right`、`half-sbs` |
| 右左（眼别翻转） | `rl`、`rlf`、`right-left` |
| 上下 | `tb`、`htb`、`ou`、`hou`、`3dv`、`over-under`、`top-bottom`、`half-ou` |
| 下上（眼别翻转） | `bt`、`btf`、`bottom-top` |
| 单目 | `2d`、`mono` |
| 裸 `3d` | 按 HereSphere，等于左右 |

三家打架的地方，我们的取舍：

- **`vr180` 算等距柱状，不算鱼眼。** SKYBOX 把 `F180`/`VR180` 都归为鱼眼，
  但 Google 定义 VR180 这个格式时指的就是等距柱状 180 左右，绝大多数带这个标记的
  文件也确实是。`F180` 保持鱼眼（三家一致）。
- **鱼眼镜头型号默认就是左右。** HereSphere 明确说 MKX200 这类一定是 SBS，
  所以有镜头标记但没有立体标记时不按"无标记=单目"处理。
- **只有立体标记、没有投影标记时看分辨率**，而不是像三家那样一律当平面 3D 电影：
  2:1（两只眼睛各是正方形）→ VR180；3.55:1（两个 16:9）→ 平面 3D；4:1 → 立体 360。
- **`rl` / `bt` 会翻转眼别。** 左眼在后半张图里，所以要选"右"才能看到左眼。
- **镜头 FOV 不会被写进 `mpv360/fov`。** `MKX200` 的 200° 是**镜头视场**，
  而 `fov` 是**观看视场**（画面里能看到多少），两者含义不同，混用只会把画面拉近。

**加新规则前先加测试用例。** 边界规则之间是互相干扰的（`eac360` 里有 `360`、
`hsbs` 里有 `sbs`、`fisheye190` 里有 `fisheye`），改对一个很容易碰坏另一个：

```bash
dotnet run --project tests/VideoFormatTests
```

38 个用例，全部来自三家文档里的原例、或者三家打架时我们做取舍的地方。
纯控制台程序，不依赖任何测试框架 —— 被测的是一个纯函数，失败就返回非零。 自动识别的结果不写盘 —— 对那个 2:1 的歧义
（mono 360 和 VR180 左右分辨率一模一样），识别永远只是猜；而"记住的模式优先于识别"，
一旦把猜测存下来，以后识别算法改好了这个文件也翻不了身。存的是**你的修正**，不是我们的猜测。

## 连续播放和外挂字幕

打开一个文件，**整个文件夹自动成为播放列表**（按文件名排序，`show2` 排在 `show10`
前面 —— mpv 用的是数字感知排序，跟资源管理器一致）。视频以外的文件不会混进来。

- 菜单：播放 → 上一个文件 / 下一个文件（到头了会自动变灰）
- 按键：`<` `>`
- uosc 控制栏上的上一个/下一个按钮，和它的播放列表面板（要浏览整个文件夹用这个）

### observe_property 的第一个值差点被丢掉

菜单项一度是灰的，但 `<` `>` 有用，切一次文件之后菜单又好了 —— 这个组合恰好指出了病灶。

`observe_property` 会**立即**推一次属性的当前值（实测确认：observe 之后没有任何操作，
马上收到 6 条 playlist）。而 `Ready?.Invoke()`（窗口在这里订阅 `PropertyChanged`）
原本排在整个 observe 循环**之后**，于是所有这些第一次的值都发给了空气。

大多数属性掩盖了这个问题 —— 文件加载时它们会再变一次，自己就好了。`playlist` 不会：
在你切文件之前它不再变化。`<` `>` 一直有效，因为那是直接发给 mpv 的，根本不经过这条路。

修法是把 `Ready?.Invoke()` 挪到 observe 循环**之前**。这一条修的不只是播放列表，
而是所有观察属性共有的一个竞态。

**字幕会自动挂上。** 视频旁边同名的 `.srt` `.ass` `.ssa` `.sub` `.vtt` 等自动成为字幕轨，
在 字幕 → 字幕轨 里直接选，不用再去找文件。用的是 `sub-auto=fuzzy` 而不是 `exact`：
`exact` 只认 `movie.srt`，`fuzzy` 连 `movie.zh.srt`、`movie.eng.ass` 一起收，
而字幕在现实里就是这么命名的。

这两条都是 mpv 自己的选项（`autocreate-playlist=filter` / `sub-auto=fuzzy`），
没有自己去枚举目录。**这正是重点**：菜单、uosc 的播放列表面板、`<` `>` 按键
看到的是同一个 mpv 播放列表，不会出现三套各自维护、互相对不上的顺序。

一个细节：外挂字幕在菜单里显示**文件名**，不是 mpv 给的 title。mpv 给自动加载的字幕
起的名字是视频主名之后剩下的部分，实测 `ep01.srt` → `srt`、`ep01.zh.srt` → `zh.srt`，
用户认得的是文件名。

## 模式切换栏

控制栏上的 **VR 按钮**（立方体图标，带当前投影徽章）点一下就展开，或按 **`Tab`**。四行：

- **投影** — 平面 / 180 / 360 / 鱼眼 / 柱面 / EAC
- **立体** — 2D / 3D 左右 / 3D 上下（当前投影不支持的会灰掉，不可点）
- **眼别** — 左 / 右 / 双眼（2D 片源时这行显示"(单目片源)"）
- **视角** — − / 当前 FOV / + / 复位

从 2D 切到 3D 时眼别会自动落到"左"而不是"双眼"：**双眼是把两只眼睛并排画到屏幕上**，
那是头显的用法，平面显示器上是错的。

**视角会停在画面边缘。** 180 片源只有半个球，转过头就是一大片空白 —— 现在会在边界停住。
能转多少取决于覆盖范围和视野：180 的片源配默认的 80° FOV，左右各有 (180-80)/2 = 50° 余量；
FOV 开到 180 就一点都转不动了（画面已经填满屏幕，这是对的）。

### 默认 FOV 为什么是 80°

**这是畸变上限，不是头显参数 —— 抄头显的数字恰恰是错的。**
头显里镜头会把屏幕重新映射回角度，渲染 105° 你的眼睛就接收 105°，两边抵消，畸变为零。
显示器没有这套光学：它在你眼中只张开 30-40°，渲染多少都被压进这个角度里，
直线投影（rectilinear）的拉伸就原样显露出来。

直线投影下，水平半角 t 处的物体横向放大 `1/cos²t`、纵向 `1/cos t`，
两者之比 `1/cos t` 就是人脸「变胖」的倍数：

| 水平 FOV | 边缘人脸变宽 | 180 片可转余量 |
|---|---|---|
| 70° | +22% | ±55° |
| 80°（当前默认） | +31% | ±50° |
| 90° | +41% | ±45° |
| 105° | +64% | ±37.5° |
| 120° | +100% | ±30° |

120° 是 mpv360 自己的默认值（`fov=2.1` 弧度），边缘的人整整宽一倍。
全景摄影那边的结论一致：直线投影 90° 以下良好、120° 以上拉伸严重，
镜头设计里 40-60° 才叫「正常透视」。

选 80 而不是 70，是因为 +31% 只出现在最外沿（半程处只有 5%），而 70° 窥视感偏强。
两者都站得住，**超过 90° 不行**。

改这个值要三处同步：`PlayerModeController.FovDegrees`、`mpv360.conf` 的 `fov=`（弧度）、
`vrmenu.lua` 里 `state.fov` 的初值。conf 里那个是桥接层连上之前那一瞬显示的值，
不一致就会每次启动画面跳一下。
360 片源水平方向自己闭合，没有边界，照旧可以一直转。
上下的余量还要看窗口形状（竖直 FOV 由水平 FOV 和窗口宽高比算出），所以改变窗口大小会重算。

**鼠标左键拖动画面即可转视角** —— 拖过整个窗口宽度正好转一个 FOV，和窗口大小、显示器缩放无关。
拖动时头部追踪暂时冻结，松手时以当前头部姿态为新的中立位，所以交还的瞬间画面不会跳。

不生效的话检查两件事：

1. **`--synthetic=mouse` 没关**。那是给没有摄像头的机器用的**假追踪器**，它把光标位置直接
   当成头部角度，所以鼠标一动画面就转、什么都点不了。默认已经是"不开追踪"（`--source=none`），
   只有显式加了这个参数才会出现。
2. **底部约 18% 是控制栏区域**，在那里按下不会开始拖动（否则点按钮就会转画面）。
   模式面板打开、或菜单栏展开时同理。

### 为什么拖动是在桥接层用 Win32 实现的

uosc 用 forced binding 独占了 `MBTN_LEFT`。它有一条"自己不用的点击转发给别的脚本"的路径，
但实测转发从未到达我们；而把优先级抢过来会让 uosc 所有按钮失灵。所以桥接层直接在
操作系统层面看鼠标，绕开 mpv 的输入路由。代价是拿不到"光标是否在 UI 元件上"这个信息，
所以上面那两个排除区域是显式写死的。

相关设置在 `bridge.config.json` 的 `input` 段。

不开菜单的快捷键：`Ctrl+Shift+G` 循环投影、`Ctrl+Shift+D` 循环立体格式、`Ctrl+Shift+Y` 循环眼别。

**"3D" 在普通显示器上只是选左眼还是右眼**，不是输出立体画面。那一行的真实含义是
"片源里两只眼睛是怎么排的"。要真出 3D 得上红蓝、3D 电视或头显。
**Flat** 不是一种投影，它是把 360 管线整个关掉，用来看普通视频。

菜单自己不存状态：它只渲染桥接层广播过来的模式，点击是发请求。所以栏上显示的
永远是播放器真实所处的模式，不会出现两边不一致。

### 投影 × 立体 的支持矩阵

mpv360 把"投影"和"立体排布"压成了一个枚举，所以有些组合根本不存在。我们的着色器
fork（`mpv/shaders-src/mpv360-vr.glsl`）补了两个：

| | 2D | 3D 左右 | 3D 上下 |
|---|---|---|---|
| **360** | ✅ 0 | ✅ **8（我们加的）** | ✅ 4 |
| **180** | ✅ 3 | ✅ 2 | ❌ 无 |
| **鱼眼** | ✅ **9（我们加的）** | ✅ 1 | ❌ 无 |
| **柱面** | ✅ 5 | ❌ | ❌ |
| **EAC** | ✅ 6 | ✅ 7 | ❌ |

选到不支持的组合时，桥接层会退回该投影下可用的排布并在 OSD 上说明，而不是默默用错的。

## 片源格式（180 VR / 360 / 鱼眼）

**mono 360 和 VR180 左右眼（SBS）都是 2:1** —— 7680x3840 既可能是"整个球面"，
也可能是"两只 180° 的眼睛并排"，视频流里没有任何字段能区分。所以自动识别只能靠文件名，
认不出来时退回 360（更常见、更安全），并在控制台打印它是怎么猜的、以及怎么覆盖。

手动指定：

```bash
dotnet run --project src/HeadTrackBridge -- --projection=vr180 "G:\test_8k.mp4"
```

`--projection` 取值：`auto`（默认）、`equirectangular` / `360`、`dual-half-equirect` / `vr180`、
`half-equirect`、`dual-fisheye`、`cylindrical`、`eac`，或直接给 mpv360 的索引 `0`–`7`。
另有 `--eye=left|right|both`（平面屏幕默认取左眼）。

投影和眼别只在文件加载时写一次，**不进每帧的写入循环** —— 否则你按 `Ctrl+Shift+p`
想手动循环投影格式时会被立刻覆盖掉。运行期间仍然可以用 mpv360 自己的按键改。

## 8K 注意事项

在 7680x3840 HEVC 51 Mbps 片源 + RTX 5060 Ti 上实测出来的三个坑，全部已修：

**1. `hwdec` 不能用 `auto-safe`。** 它在这台机器上解析成 `d3d11va-copy`，每帧都把
~47 MB 读回系统内存，解码吞吐直接腰斩。`--vo=null --untimed`，300 帧实测：

| hwdec | fps |
|---|---|
| nvdec | 35.9 |
| d3d11va | 32.7 |
| 软解 | 34.4 |
| **d3d11va-copy（auto-safe 选的）** | **17.0** |

**2. `hwdec` 必须和 `gpu-api` 匹配。** nvdec 虽然最快，但它是 CUDA interop 路径，
mpv 在 d3d11 后端上会拒绝它（日志：`CUDA hwdec only works with OpenGL or Vulkan
backends`）然后**静默退回软解**。配 `gpu-api=d3d11` 就得用 `hwdec=d3d11va`。
这个坑很隐蔽，因为它不报错、只是变慢。验证：

```bash
mpv --config-dir=mpv --term-status-msg='${hwdec-current}' <file>
```

输出是 `no` 就说明没生效。

**3. mpv360 的着色器默认按源分辨率跑。** 上游写的是 `//!HOOK MAINPRESUB` 但没有
`//!WIDTH` / `//!HEIGHT`，所以着色器对**每个源像素**执行一次 —— 8K 片源就是 2950 万像素，
跟窗口多大无关；算完的 8K 结果再缩放到窗口，而这个缩放本身是整条管线里最贵的一步。
`tools/install-mpv360.ps1` 会自动打上补丁，让它直接按输出分辨率采样，两笔开销一起省掉。
这是安全的：`render()` 本来就是用 `target_size` 算视锥的，不是用被 hook 的纹理尺寸。

| 窗口 | 补丁前 | 补丁后 |
|---|---|---|
| 1920x1080 | 7.5 fps | 9.4 fps |
| 3840x2160 | 4.3 fps | 9.1 fps（与分辨率无关了）|

三个都修完后的实际播放：`hwdec-current=d3d11va`、`estimated-vf-fps=30.0`、
**`frame-drop-count=0`**，满帧不掉帧。

### 60fps 的 8K 片子会变慢动作，不是丢帧

这台机器上 8K HEVC 的解码天花板大约 **33–35 fps**（上表两次独立测量都指向这个数）。
片源要 59.94 fps 的时候，差额没有地方可去：

```
container-fps            = 59.94
hwdec-current            = d3d11va      解码器在跑
decoder-frame-drop-count = 0            但一帧都没跳过
time-pos / 墙上时钟      = 0.21         实际播放速度
```

**关键在 `framedrop=vo`：它只在输出端丢帧，不会跳过解码。** 解码是瓶颈的时候，
每一帧仍然必须解出来，于是整条管线跟着解码器走，播放就成了慢动作 —— 不是"扔掉多余的帧、
按原速播"。这是 mpv 的设计，不是 bug。

`framedrop=decoder+vo` 能让它在解码前就跳过部分帧（实测 0.26 → 0.41 并还在往上爬），
但只能跳非参考帧，补不满这个缺口，而且会带解码瑕疵。**没有设成默认**：对解码跟得上的
片子它毫无作用，对跟不上的片子它用画质换速度，这个取舍应该由人来做，不该悄悄替用户决定。

实际能解决的只有三条：换 30fps 或更低分辨率的片源、换解码更快的机器、或者接受慢动作。

> 之前这里写过"解码跟得上、是 30Hz 显示器在丢帧"，那是错的。当时依据的
> `estimated-vf-fps` 在跟不上的情况下会回显 container-fps，不是真实吞吐；
> 用墙上时钟对 `time-pos` 才测得出来。显示器确实是 30Hz，但那是另一件事。

其余：

- 片源常见 100–200 Mbps，机械硬盘可能喂不饱；`demuxer-readahead-secs` 已拉到 20。
- `profile=fast` + `bilinear` 是刻意的：8K 下 GPU 预算全给解码和投影着色器。
- 平面屏幕只需要一只眼，立体片源用 `Ctrl+Shift+e` 选。
- 按 `Ctrl+Shift+i` 随时看 dropped frames。
